# Ai

## AI agents and tools
Put agents in `app/Ai/Agents` named `*Agent` with `#[MaxSteps]`, task-resolved models (never hardcoded) and `UsesFailoverChain`: `use RunsAsAiTask` and declare `aiTask()` — the trait supplies `model()`/`modelSelection()` from `TaskModelResolver` and a `providerOptions()` that sends the task's reasoning through `ReasoningOptions` (mapped and clamped per provider in the failover chain) plus OpenRouter routing; never hand-write `providerOptions()` reasoning; put tools in `app/Ai/Tools/&lt;Service&gt;` named `*Tool` extending `BaseTool` (the DecisionAgent's tools extend `DecisionTool`, see below), implementing only `description()`, `risk()`, `execute()`, and `schema()`. Never call an upstream API from a Destructive tool — return `['type','target_service','payload']` and let `BaseTool` queue an `ActionRequest`. Per-run state lives in a container-bound `*RunContext`, since the SDK resolves tools fresh from the container.

## Sub-agents
Sub-agents are `*Agent` classes in `app/Ai/Agents` implementing `CanActAsTool` (stable `name()`), `HasStructuredOutput`, `#[MaxSteps]` and `#[RepairToolCalls]`, each running as its own `AiTask` (taking the conversation's reasoning level on its own model). They are read-only; the parent keeps destructive tools. Their usage rows carry `parent_invocation_id`.

## Tool argument validation
`BaseTool::handle()` (and `DecisionTool::handle()`) validates every call against rules derived from the tool's own `schema()` (`ToolArgumentRules`, built on `JsonSchema::rules()`) before `execute()`, so types, enums, required keys and nested items need no hand-written rules. A required-but-nullable field may be omitted and `""` on an optional field counts as omitted. Use `$request->validate([...])` inside `execute()` only for what a schema can't express (ranges like `min:1`, regex, `required_if`/cross-field rules, `distinct`); put custom wording in `argumentMessages()` and pass it to that `validate()` too so both stages word a field alike. Either failure becomes `{error: invalid_arguments, errors}`. Keep `InvalidArgumentException` for domain/state checks.

## Per-step middleware and provider-gated tools
Agent middleware (1.0) wraps each step: `handle(PendingStep, Closure): mixed` in `app/Ai/Middleware`; tool-using agents use `AnswerOnFinalStep` + `EnforceBudgetEachStep`; MediaAgent adds `Stop::when()` on `ClientConnection::disconnected()`; structured sub-agents add the throwing `StopWhenClientDisconnected`; `PriceFetcherAgent` adds `StopWhenPriceRefreshOutOfTime` (a no-op unless `RefreshAiPricesJob` opened the `PriceRefreshTimeBox`), which stops the run once the box no longer fits another step and cuts each step's provider timeout to the time left; `WebFetchTool` checks the box before every request (`PriceRefreshTimeBox::WEB_FETCH_SECONDS`) and answers `out_of_time` instead of fetching, so parallel fetches cannot overrun it (the provider-native WebFetch mode is bounded only by the step timeout). `RecordAgentUsage` and `ConversationStore` treat any `cancelled` stream as a user stop (`StoppedByUser::response()`), so a `Stop` on another streamed agent is billed and saved as a user stop. Register provider tools (`CodeExecution`) only when `ProviderCapabilities::everyProviderSupports()` is true for the whole failover chain — since laravel/ai 1.1 the SDK silently drops a provider tool the reached provider lacks, so an ungated agent quietly loses the tool its instructions promise on a failover. Register a `ToolSearch` when `ProviderCapabilities::primarySupports()` is true for the chain's first provider: the SDK (1.4.1, `TextGenerationLoop::toolsSupportedBy()`) inlines its deferred tools on a fallback without tool search, so the fallback keeps every tool and only sends a larger payload (`ProviderToolSupportCharacterizationTest` pins both behaviours).

A step-gating middleware must never exempt `PendingStep::isFirstStep()` to skip its own check "because the caller already checked once before prompting": a provider failover (`UsesFailoverChain`) re-runs the whole agent loop on the fallback provider starting at step 0 again, so an `isFirstStep()` exemption lets that restarted step run unchecked. Check every step, including step 0; a redundant check on the very first provider's own step 0 is harmless.

## Structured sub-agents run unstreamed
Since laravel/ai 1.2.2 `AgentTool::stream()` calls `handle()` (a plain `prompt()`) for any HasStructuredOutput agent, even inside a streamed parent turn, so a structured sub-agent yields no stream events and its chat tool chip shows no activity line. Do not override `stream()` on a sub-agent to get activity back — the SDK never calls it. Every HasStructuredOutput sub-agent uses `App\Ai\Concerns\ActsAsStructuredSubAgent` for the shared step middleware. Test sub-agents through the parent's stream(), not only prompt().

## Agents own their failover chain
Every agent uses `App\Ai\Concerns\UsesFailoverChain` and implements `modelSelection()`: `provider()` returns `AiSettings::providerChainFor($this->modelSelection())` — always an explicit `[provider => model]` map plus the failover — which laravel/ai reads whenever `prompt()`/`stream()` get no provider. Never pass `provider:` at a call site — sub-agents run through `AgentTool` with no provider and only fail over through the concern. AI-layer traits live in `app/Ai/Concerns` (like the SDK's `Laravel\Ai\Concerns`), not `app/Concerns`.

## Decision tools extend DecisionTool, never BaseTool
The DecisionAgent's tools live in `app/Ai/Tools/Decision` and extend `DecisionTool`: no advisory-mode gate and no auth-bound queueing — they dispatch through `ActionOrchestrator::dispatchFromAgent()` with the run's `DecisionRunContext` (which stays in `app/Ai/Decision`). The base owns context resolution, the capability refusal hook, the per-run cap, JSON encoding and `invalid_arguments` from the schema check or `$request->validate()`. Keep their domain rejections (`subject_mismatch`, `subject_not_verifiable`, `capability_disabled`, `type_not_allowed`, `replacement_in_flight`, `missing_target`, `dispatch_failed`, `no_action_type_config`, `lookup_failed`, `nothing_importable`, `second_opinion_rejected`, plus the base's `no_active_run` and `max_actions_reached`) byte-for-byte: the DecisionAgent prompt and the security hardening tests depend on them. Every proposal goes through `ActionOrchestrator::dispatchFromAgent()` with the run's context and is tallied with `DecisionRunContext::recordDispatched()`, so the second opinion (per action type, `SecondOpinionVerifier`) applies; its rejection result never carries the verifier's reason.

## Benchmark replay hooks every agent and tool
The benchmark runs real agents with their tools swapped for `App\Ai\Benchmark\ReplayTool`, so every agent's `middleware()` must end with `ReplayBenchmarkTools` (it is a no-op outside a `BenchmarkRunContext`); structured sub-agents get it from `ActsAsStructuredSubAgent`, so never override their `middleware()` without it. A new tool base class must be handled by `WriteToolDetector::writes()`, or its mutating calls are replayed as lookups instead of captured as intended actions. A read tool that is pure (its result depends only on its arguments, with no HTTP, database, cache, file or run-state access; today only `OfferChoicesTool`) implements `App\Ai\Benchmark\RunsInReplay`, and replay runs it for real instead of answering from fixtures; never mark a tool that reads anything. Tool telemetry (`RecordToolInvocation`, `RecordToolFailure`) records `ReplayTool::unwrap($tool)::class`, never the wrapper. Usage rows written inside a benchmark run carry `benchmark_run_id` (from `BenchmarkRunContext::runId()`); the run's cost is the sum of those rows, and AI Usage tool stats never mix them with live calls (the "Only benchmarks" filter shows the replays alone, every other filter leaves them out), so a new usage writer must set that column and a new tool-stat query must split on it.

## A reviewer's outcome outranks the cascade LLM's
Classification outcomes record who settled them in `outcome_source` (`ClassificationOutcomeSource`). For the second-opinion gate a human review is the ground truth: `SecondOpinionVerifier::resolveFromReview()` settles open rows and replaces an outcome the JevThenLlm cascade's LLM recorded, never a reviewer's own, and the LLM only ever settles open rows, so it never overwrites a human outcome (owner's rule, 2026-11-24).
