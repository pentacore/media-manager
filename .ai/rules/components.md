# Components

## Component placement and imports
Put shadcn-vue primitives in `components/ui/&lt;kebab-folder&gt;/`, house design-system primitives in `components/mm/`, feature components in `components/&lt;feature&gt;/`, and app-shell components at the root. Name files PascalCase and import via the folder's `index.ts` barrel, not deep file paths. Icons are `@lucide/vue` named imports sized with Tailwind classes.

## Calendar days open a day popover
In `CalendarMonthGrid` a day with items is one `PopoverTrigger` button (`[data-calendar-day-open]`) holding the day number, at most three compact rows and "+N more"; its `PopoverContent` (`[data-calendar-day-popover]`, portalled to `<body>`) lists every item of the day as the full `CalendarItem` row with its Search/Monitor actions. Compact rows are plain `<span>` text, never links or buttons, because they sit inside the trigger button; put any new per-item control on the full row. A day without items has no trigger. Below `sm` the trigger shows one `aria-hidden` dot per item (at most three, then `+N`, `[data-calendar-day-dots]`) instead of the compact rows, which sit in a `contents max-sm:hidden` wrapper (`[data-calendar-day-rows]`). The popover then spans the screen with `collision-padding` 16 (the query feeds only the popover, never SSR markup), and the page opens in Agenda (`matchMedia` in `onMounted`). `CalendarPhoneTest` pins the phone side. `tests/Browser/CalendarTest.php` pins it.

## Page headers use PageHeader
A page's hero header (title block on the left, actions on the right) is `PageHeader` from `@/components/mm`, never a new hand-rolled `flex … justify-between` row. Hand-rolled headers that already wrap at 375 px are deliberate exceptions until a later batch adopts them: `Anime/Season.vue`, `Library/Wanted.vue`, `Admin/Benchmarks/Runs/Show.vue`, `Admin/MediaReplacement/Attempts/Show.vue`, `Sonarr/Series/Create.vue`, `components/ai-prices/PricesHeader.vue`, `components/ai-usage/UsageHeader.vue` and `Whisparr/Show.vue`. The series and movie detail toolbars are on `PageHeader` too (the Back button in `#title`, Monitor/Search as `#primaryAction` with `primary-first`, the rest in `#secondaryActions` and `#menu`); the Whisparr show page's toolbar (an admin page that already wraps) stays hand-rolled. Pass the original elements into its slots: `eyebrow` (the `mb-1.5` breadcrumb line), `title` (the `h1`), `description`, `filters` (controls that stay visible on a phone), `secondaryActions` (inline buttons, desktop only), `primaryAction` (the one action a phone keeps) and `menu` (`DropdownMenuItem`s mirroring `secondaryActions` for the ⋯ menu below `sm`; same handlers and URLs, each with `data-page-header-item="<key>"`). Put a condition that removes a whole slot on its `<template v-if … #slot>` so the header can drop an empty actions row and never shows an empty menu; set `primary-first` when the primary action came first, `align` from the old row's `items-*`. At `lg` and up the layout is the old row, pixel for pixel; between `sm` and `lg` the row wraps (the title block keeps up to 12rem of its own width, and actions that do not fit beside it move to their own line and wrap there), so never put `sm:flex-nowrap` back on it. `ActivityStatisticsPhoneTest` pins it at 769 px with a fine pointer. `PageHeaderTest` pins the phone menu, its keyboard model, the desktop row and each migrated header at 375 px; the layout gate (`tests/Browser/MobileLayout/`) pins the whole pages listed in its member and admin datasets at 375 px and 1440 px, light and dark; `DetailToolbarPhoneTest` pins the series and movie toolbars. A dialog that a `#menu` item opens takes `@close-auto-focus="returnFocusToPageHeaderMenu($event, '<its trigger selector>')"` (`@/lib/pageHeader`): below `sm` its `DialogTrigger` sits in the hidden `#secondaryActions`, so Reka's focus restore would drop focus to `<body>`; the helper sends it back to `[data-page-header-more]` and leaves desktop's restore alone. The app-wide `useConfirm()` dialog has no trigger at all, so a question asked from a `#menu` item passes `onCloseAutoFocus: (event) => returnFocusToPageHeaderMenu(event, '<desktop trigger>')`; a dialog component a menu item opens re-emits `close-auto-focus` (`InteractiveSearchDialog`, `ReplaceFileDialog`).

## Settings rows use SettingsRow
A label-beside-control settings row is `SettingsRow` from `@/components/mm`: `<SettingsRow><template #label><Field …/></template><control/></SettingsRow>`. Never write an inline `style="grid-template-columns: 200px 1fr"` (or any fixed `grid-template-columns` style): a fixed or `1fr` track has an automatic minimum, so a wide control stretches the row past a phone screen. `SettingsRow` is `grid-cols-1` below `sm` (label above control) and `200px minmax(0,1fr)` with `gap-6` from `sm` up. `SettingsRowTest` pins both widths. To use a wide screen, wrap a section's rows in `SettingsGrid` (one column below `xl`, two from `xl`, three from 1800 px; `:max-columns="2"` stops at two): rows fill left to right in source order, a `SettingsRow` inside stacks its label above the control again from `xl` up, and `<SettingsRow wide>` spans the grid and keeps the label beside the control (for a list, table, textarea or chart). A section's heading and description stay above its grid, and a page that uses one lifts its cap only from `xl`, so below 1280 px nothing changes. A page lifts it in one of two ways: the settings layout takes the `wide` layout prop (its section stays `max-w-2xl` below `xl` and gains `xl:max-w-none`), and a page with its own root keeps its own cap below `xl` and adds `xl:max-w-none` (`max-w-3xl xl:max-w-none`). A divider between rows grouped into one grid stays below `xl` as `<Separator class="col-span-full xl:hidden" />`, so the phone layout keeps it. Write the 1800 px step as `xl:min-[1800px]:`: Tailwind emits a bare `min-[1800px]:` query before `xl:`, so `xl:grid-cols-2` would win. On a settings-layout page that opts in (`layout: { wide: true, … }` in its `defineOptions`: Profile, Preferences, Security) every block that is not a grid (Profile's Emby card and DeleteUser, Security's two-factor card) keeps its own `max-w-2xl` and `data-settings-capped`. Notifications and Appearance never opt in. The Decision Agent and Media Replacement pages follow the root pattern. A form that is not built from `SettingsRow` (the connection forms, the benchmark schedule form, AI Models) wraps its existing field blocks in `SettingsGrid` unchanged (label above the control, as they were) and passes `class="gap-y-4"` (or `gap-y-6`) to keep the gap it had below `xl`; a list, table, textarea, mapping block or preview is `col-span-full`, and the Save/actions row stays below the grid (a text-led full-width block that should not stretch also keeps `max-w-2xl` and `data-settings-capped`). A task row that was label-beside-control (`md:grid-cols-[200px_1fr]`) adds `xl:grid-cols-1` so it stacks inside a column, and AI Models pins `:max-columns="2"` because its rows hold tier editors, and the connection forms pin it because they hold only a handful of long fields (a third column would sit half empty); the schedule form keeps three. A form whose plain fields are each separated by full-width blocks keeps its cap and gets no grid, since there is nothing to pair (`Benchmarks/Runs/Create`), and so does a page with nothing to pair; the two composite editors (`Benchmarks/Cases/Form`, `AI/Templates/Edit`) keep `max-w-[900px]` below `xl` and use their own two-column layout from `xl` instead (see "Composite editors go two-column from xl"). `WideSettingsLayoutTest` pins the columns on AI Settings, Decision Agent, Media Replacement, Profile, Preferences, Security, the connection forms, the benchmark schedule form and AI Models, and that the run form, Appearance and Notifications stay capped (a page's measuring helpers take a row or block expression, never a page-specific global).

## A settings row links its label to its control
An editable row passes `for` to its `Field`, which then renders a real `<label for>` with the id `<for>-label` (its hint gets `<for>-hint`); without `for` it stays the old `<div>`, so read-only fields keep no `for`. When the Field has a hint, the control takes `aria-describedby="<for>-hint"`: the control sits in `SettingsRow`'s default slot, outside the Field, so each call site wires it. Use the control's existing id, else a new kebab-case id prefixed by the page (`preferences-time-format`), and `useId()` inside a repeated component. A native `Input`, `Textarea`, `PasswordInput` or checkbox needs only `for` plus its `id`. A button-based control also gets `aria-labelledby`: a `Toggle` takes `aria-labelledby="<for>-label"` (it is `role="switch"` with `aria-checked`, and hides its on/off text once labelled), and a `SelectTrigger` takes `aria-labelledby="<for>-label <for>"` so its value stays in its name. A row with several controls (or a checkbox list) never uses `for`: a `<label for>` may only point at a labelable element (input, select, textarea, button, meter, output, progress), never a `div`. It passes `label-id="<base>-label"` to the Field, which keeps the label a `<div>` with that id (the hint gets `<base>-label-hint`), puts `role="group"` and `aria-labelledby="<base>-label"` (plus `aria-describedby="<base>-label-hint"` when the Field has a hint) on the control wrapper, and names each control on its own (Preferences' timezone filter and select; a Toggle in a group may take the row label too; `ModelSelect` and `ReasoningSelect` take an `aria-label` prop, which they render as an `sr-only`, `aria-hidden` span (`useId()`, with `data-select-name` as the test hook; `aria-labelledby` still reads a hidden node it points at, and browse mode no longer reads the name twice) and point the trigger's `aria-labelledby` at it plus the trigger itself, so the selected value stays in the name; a `v-for` row builds its ids from the loop key, as AI Models' `ai-models-<task>-label`). A `Field` outside a `SettingsRow` (chat template editor, AI Models) follows the same recipe. A checkbox that keeps its own inline text inside a wrapping `<label>` (so a click on that text still toggles it once) has two labels, which browsers would join into one long name, so it also takes `aria-labelledby="<for>-label"` (the row label alone names it), and its text becomes `<span id="<for>-description">`, listed before the hint in its `aria-describedby` (`"<for>-description <for>-hint"`). Chromium already names a button from its `<label for>`; the `aria-labelledby` keeps that explicit for other engines. `SettingsLabelTest` checks every editable row on the member and admin settings pages, that no `label[for]` points at a non-labelable element, that every control inside a labelled group has a name, that every linked Field's hint (`data-field-hint`) describes a control or group, the checkbox rows' computed names (Playwright's role selector) and text clicks, and the desktop label box; `ToggleTest` pins the switch and a label click toggling it once.

A `Toggle` outside a settings row is named the same way, never by its on/off `label` text (that only repeats `aria-checked`): `aria-labelledby` pointing at the heading or label beside it (WebhookLog's "Capture & store", the schedule form's "Enabled" heading, the destination form's `Label`, ReplaceFileDialog's "Verify subtitles" with its line as `aria-describedby`), or, in a table row, an `aria-label` built from the row and its column (`` `${rule.label}: enabled` ``). Either one hides the on/off text from assistive tech. A `label` prop that is a fixed name rather than a state (Bazarr's "Scheduler enabled", "Hide acknowledged") already names the switch and needs neither. `ToggleNamesTest` checks these sites with `switchNameScript()` from `tests/Pest.php`; `selectNameKeepsValueScript()` there checks a `ModelSelect`/`ReasoningSelect` name keeps its value (the chat model picker passes `aria-label` and hides its visible "Model"/"Reasoning" text).

## Collapsible triggers seed reka's contentId
reka-ui's `CollapsibleContent` fills the root context's `contentId` in its own setup, after the trigger has rendered, and the context is a plain object, so a closed trigger used to keep `aria-controls=""` until something re-rendered it. `ui/collapsible/CollapsibleTrigger.vue` therefore seeds it in setup (`injectCollapsibleRootContext().contentId ||= useId(undefined, 'reka-collapsible-content')`), and the content's own `||=` keeps that id. Always use the `ui/collapsible` wrapper, never reka's `CollapsibleTrigger` directly, and never re-key a trigger to refresh its id. The closed content element stays in the DOM, hidden and empty, so the id always resolves. `CollapsibleTest` pins NavMain, TemplateHelp, the Login email form and `SeriesSeasonCard`.

## Dialog and sheet close buttons stay on screen
`DialogContent` and `SheetContent` scroll their own content, so their close X must not scroll with it. Below `sm`:
- **`SheetContent`'s X (a right-side sheet)** is `max-sm:fixed`, because the sheet is full width there and has no transform after its slide-in — it stays pinned to the viewport while the sheet's own `overflow-y-auto` scrolls under it. It carries `data-sheet-close`.
- **`DialogContent` itself stops scrolling below `sm`** (`max-sm:overflow-hidden`, overriding its own base `overflow-y-auto`). Its real content is wrapped in `[data-slot="dialog-body"]` — `display: contents` at `sm`+, so it has **no box there at all** (same "a wrapper div that paints nothing" exemption as elsewhere; it never needs a parity-capture `ignored` entry) and desktop's DOM/layout are unchanged. Below `sm` it is a `flex flex-col` column and the thing that actually scrolls (`max-sm:overflow-y-auto`, `max-sm:overflow-x-hidden` so a child's own negative margin can never cause a horizontal scroll wobble; `max-sm:-mx-2 max-sm:px-2` is the matching gutter, sized to the `-mr-2`/`pr-2` pattern dialog bodies already use for their own inner scrollers, e.g. `InvocationDetailDialog`; `max-sm:-mb-2 max-sm:pb-2` is the same gutter at the bottom, so the 40 px `touch-target` `::after` of a footer `Button` (36 px, or 32 px for `sm`) ends inside the body's padding instead of making it scroll by a 2–6 px sliver — never patch a footer button for an overhang of up to 8 px, which this gutter covers). The X keeps its original place in the DOM (after the body wrapper) and stays plain `absolute top-4 right-4` at **every** width (plus `max-sm:z-10 max-sm:rounded-full max-sm:bg-background` for the phone pill look): since `DialogContent` itself never moves, an `absolute` sibling positioned relative to it never moves either — "stays on screen while the body scrolls" without `sticky`.
- **Desktop** is unchanged either way: `DialogContent` keeps `grid`/`overflow-y-auto` and the X keeps `absolute top-4 right-4`.

A consumer that needs this to work must know:
- **the gap is inherited, not hard-coded.** `[data-slot="dialog-body"]`'s `max-sm:gap-[inherit]` takes whatever `gap-*` the consumer set on `DialogContent` itself (the default is `gap-4`; `CommandPalette` overrides it to `gap-0`). Don't reintroduce a fixed `max-sm:gap-*` on the body — it would fight a consumer's own gap.
- **a direct child that is itself a scroll container (`overflow-y-auto`, `max-h-*`) shrinks below `sm`,** because flex items default to `min-height: auto` only when `overflow: visible`; one with its own `overflow` has an automatic minimum of 0 and absorbs the body's available height instead of forcing the body to scroll past it. This is neutral-to-better for a component built as an inner scroller (`InteractiveSearchDialog`, `ReplaceFileDialog`, the command palette's results list), but a future direct child using `overflow-hidden`, `truncate` or `line-clamp` would get clipped instead of shown — give it `shrink-0` if it must keep its full height.
- **a phone test that needs the scroller targets `[data-slot="dialog-body"]`, never `[role="dialog"]`** — the dialog's own box no longer scrolls. `OverlayCloseTest` and `MobileContainmentTest` do this.
- a dialog whose content needs the X's corner reserves it with `pr-10`/`pr-12`.

The command palette keeps its own `max-height` media-query classes from before the `short:` variant (`flex`/`flex-col` with its `top-4`, so its direct children, passed straight through the `contents` body wrapper, become flex items that can shrink and scroll instead of grid auto-rows that overflow a clamped `max-h-*`). A new dialog needs no variant of its own: `short:` (below) already gives every `DialogContent` that layout. `OverlayCloseTest` pins the dialog, the sheet, the palette's phone gap and its landscape scrolling.

Every dialog gets the same treatment on a short viewport: the `short:` variant (`resources/css/app.css`, `max-height: 500px` — a phone turned sideways, which is wider than `sm`, and also any desktop window under 500 px tall, whatever its width) gives `DialogContent` the phone layout (`short:flex short:flex-col short:overflow-hidden`, and the `[data-slot="dialog-body"]` scroller), so a tall dialog's body scrolls under its X and its footer can always be scrolled into view. A `SelectTrigger` whose `::after` makes a dialog body or strip scroll by a few pixels takes `touch:min-h-10` at the call site, never in `ui/select`. `LandscapeDialogTest` pins the listed dialogs in portrait and landscape.

## Phone tables become PhoneCardList cards
On the phone-job pages (Action Queue, SABnzbd queue and history, grab queue, watch history, interactive search releases) a table becomes stacked cards below `sm`:
- **The table:** keep it, and give its frame `max-sm:hidden`.
- **The cards:** render them with `PhoneCardList` from `@/components/mm` (its root is `min-w-0 sm:hidden`; a `card` slot per item, an optional `empty` slot), placed **after** the table in the DOM. A wrapper around it that is itself a grid item or flex-row item needs `min-w-0` too: `break-words` does not lower the min-content width, so one long unbroken title would widen an `auto` track past the screen. The same holds for any flex-row item holding long text on a phone (`max-sm:min-w-0` beside `max-sm:break-words`, as on Now Playing and the watch-history Top user card). Desktop text clicks then keep finding the visible table first.
- **Hooks:** every hook inside a card gets its own `data-<x>-card-*` name (`data-action-card-select`, `data-sab-card-delete`), never the table row's. Pest's strict selectors count hidden elements, so a reused hook breaks every desktop test that uses it.
- **Select-all on phones:** shared components with a static hook (`BulkSelectAll`'s `data-bulk-select-all`) are not repeated in cards. Phone select-all is the compact bulk bar's ⋯ item "Select all on this page" (`[data-bulk-select-all-phone]`).
- **What a card holds:** the row's key facts and every row action, with long file or release names in `break-all` and titles in `break-words`.
- **One empty message:** a card list's `empty` slot must not repeat text that the table's own empty row already shows, because a strict `assertSeeIn` counts the hidden copy as a second match. The SABnzbd queue and history keep the table's empty row as the only message. Their table frame is `max-sm:hidden` only while it has rows, their `thead` is `max-sm:hidden`, and the `PhoneCardList` renders only when there are rows (`v-if`).

Admin-only tables keep their columns and scroll inside their frame. `ActionQueuePhoneTest`, `DownloadsPhoneTest`, `InteractiveSearchPhoneTest` and `MonitoringPhoneTest` pin the cards.

## Admin tables scroll sideways with a sticky name column
An admin table stays a table on a phone and scrolls inside its own `overflow-x-auto` frame (shadcn `Table`'s container, or the hand-rolled `overflow-hidden rounded-xl border` > `overflow-x-auto` pair). When its first column names the row and the table is wider than a phone, put `sticky-first-column` (`resources/css/app.css`, below `sm` only) on the `<table>` (`<Table class="sticky-first-column">`) with a `data-admin-table="<key>"` hook: each row's first cell stays at the frame's left edge, painted `bg-card` (tinted on row hover) with a border line on its right and its own row dividers (it covers the table's collapsed borders), capped at 45vw and held at 8rem or more. `max-width` on a cell is not reliable, so keep the first cell's content in one block-level element (wrap bare text or an inline link in a `span` with `block`); an empty-state `colspan` cell is never sticky. The utility also gives the frame scroll padding, so focus and `scrollIntoView()` land a cell beside the sticky column, not under it. Never make a checkbox or timestamp column sticky. `AdminTablePhoneTest` pins it.

## The Action Queue detail has a pane and a sheet layout
`ActionRequestDetail` is the one implementation of an action's detail, review buttons and failure/second-opinion cards:
- **`layout="pane"`** (default) is the desktop panel beside the table, `max-sm:hidden`.
- **`layout="sheet"`** renders the same markup inside `ActionRequestSheet`, the phone's full-screen `Sheet`. The card stops clipping (sticky needs a non-clipping ancestor) and the Approve/Decline and Retry rows become `sticky bottom-0` bars.

Never fork the detail for a new presentation; add a layout case.

The sheet opens on its title (`@open-auto-focus` focuses `[data-action-title]`), never on the pinned Approve, so a held Enter cannot approve and a screen reader starts at the top. It opens from a card (`openSheet`) or, on a phone, from a `?request=<id>` deep link (a request past the listed page comes as its own `preselectedRequest` prop) in `onMounted` (`openDeepLinkedSheet()`, called from the page's single `onMounted` after `subscribeLive()`: `ActionQueueLiveListTest` re-runs the page's only mounted hook, so never add a second one). On close it focuses the card and brings it back into view with `scrollIntoView({ block: 'nearest' })`, not a saved `scrollY`, because a live row can be added above it meanwhile; when the card has left the list or has no box (the viewport crossed `sm`), focus goes to the page `h1` (`focusPageHeading()` from `@/lib/bulk`). Both run from `@close-auto-focus`, default prevented. Closing also drops `?request=` from the URL with a client-side `router.replace` (no new history entry), so a reload or back/forward does not reopen a deep link. The forget is sticky (re-run on every page URL change after a close) and reviews post with `replace: true`, so a visit in flight across the close cannot bring the deep link back. The page's `visibleRequests` watcher closes the sheet before it moves the selection, and the sheet renders a held row (`shownRow`, frozen once `open` turns false) with the detail `inert` while it slides out, so a row that leaves the list (approved under the Pending tab) never turns the sheet into another action, not even during the exit animation. Live status changes for a listed row need nothing extra, because the sheet renders the same `selected` row `useActionQueueLive` orders by `status_version`. An off-page deep-linked request (`preselectedRequest`) is not in the live list: a status change for it makes the debounced `statusCounts` reload also name `preselectedRequest`, a lazy prop the server re-reads only then. `ActionQueuePhoneTest` pins it.

## Bulk bars are fixed to the bottom of a phone screen
`BulkActionBar` from `@/components/bulk` takes every action in its default slot (the desktop row).
- **A phone-job surface** also passes `#primary` (the one action a phone keeps, `h-10`) and `#menu` (`DropdownMenuItem`s for the rest). Below `sm` the bar is then one `h-14` row: the count, the primary action, and ⋯ (`[data-bulk-more]`) with the menu items, the over-limit note and "Clear selection". Every bar, compact or not, is `fixed` to the bottom edge of the screen below `sm` (with the safe-area inset as bottom padding), and `sticky bottom-4` from `sm` up. The sticky bar holds only because the layout's content box (`AppSidebarLayout`'s `main`) is `overflow-x-clip`, which clips without making a scroll container; `overflow-x-hidden` there (or on any other ancestor of a bar) turns that box into the sticky container while the window scrolls, and the bar then only appears at the end of the page. That box also needs `min-w-0`: unlike `hidden`, `clip` does not lower a flex item's automatic minimum width, so without it `main` grows to its content and wide pages stop truncating (breadcrumbs, tables, dialogs). `LibraryBulkActionsTest` pins the desktop bar in the viewport after a scroll. While it is mounted it sets `data-bulk-bar-open` on `<body>`, and its measured height on `<body>` as `--bulk-bar-height` (a ResizeObserver), and `app.css` then ends the page (`main[data-slot="sidebar-inset"]::after`, phone only) with that height plus 1 rem, so everything after the bar in the DOM (the Action Queue pagination, the SABnzbd history) scrolls clear of it too; a card a sheet returns to keeps a matching bottom scroll margin.
- **Hooks:** give each phone action its own hook (`data-bulk-approve-phone`, `data-bulk-menu-item="<key>"`), never the inline button's: strict selectors count hidden duplicates.
- **Phone select-all:** each adopter's `#menu` starts with "Select all on this page" (`[data-bulk-select-all-phone]`, calling the page's `setAll…(pageIds, true)`), because card lists never repeat `BulkSelectAll`.
- **A bar without `#primary`** keeps its wrapping row of inline actions at every width — the library bars do this, because their quality-profile `Select` cannot live in a menu — and is fixed to the bottom on a phone like the compact bar. There it is at most three rows: the count and Clear share the first (the actions group is `max-sm:order-last max-sm:basis-full`), then Monitor, Unmonitor and Search, then the profile `Select` and Delete… (`max-sm:order-1` in `LibraryBulkActions`, whose `SelectContent` is capped to the screen width); the measured spacer makes room for all three. Over the limit, the note stays on the first row as a short one-line "At most N at a time" (the full sentence stays for screen readers as `max-sm:sr-only`). A new library action or message must keep it to three rows. `LibraryBulkBarPhoneTest` pins it, over-limit state included.

`BulkBarPhoneTest` pins the height, the menu, select-all, the clear and the frozen state during a run.

## The AI chat is a sheet on a phone
The chat opens from the header's AI button (`[data-header-ai-chat-sheet]`, `sm:hidden`) and from the phone sidebar's "AI Assistant" button (`[data-sidebar-ai-chat]`, `sm:hidden`, which closes the sidebar first) as the full-width `AiChatSheet`, never by navigating to `/ai/chat`; from `sm` up to the sidebar's 768 px sheet breakpoint the sidebar entry is a link to `/ai/chat` (`[data-sidebar-ai-chat-link]`), matching the header link at that width; desktop keeps the header link and the ⌘J footer button. On the chat page itself neither phone entry opens the sheet (the header button is not rendered, the sidebar entry only closes the sidebar), so a second chat never stacks over the page. The sidebar entry focuses the sidebar trigger before opening the sheet, so closing the chat returns focus there. Because the sheet follows the visual viewport, its close X is positioned inside the sheet below `sm` (an arbitrary child variant on `AiChatSheet`'s `SheetContent` turns SheetContent's viewport-fixed phone X into an absolute one), so it moves with the sheet when iOS pans for the keyboard. On a phone `ChatHeader` keeps the conversation picker and a ⋯ popover (`[data-chat-options]`) with the mode buttons and `ChatModelOptions`, the single model/reasoning editor that the desktop chip's popover (`ChatModelPicker`) renders too. While renaming on a phone the picker hides and the rename row flexes, so it never overlaps the ⋯ or the sheet's fixed close X. Never fork the model controls (their override logic is `components/ai/chatOverride.ts`); `ChatSheetPhoneTest` and `ChatModelOverrideTest` pin it.

## PasswordInput takes two class props
`PasswordInput` wraps its input and the show/hide toggle in a `relative` wrapper. `class` sizes and places the wrapper (width, margin); `input-class` styles the input (height, text size). Never pass an input height in `class`: the wrapper would change size while the input keeps `h-9`, and the toggle (`inset-y-0` on the wrapper) would sit off the input's centre again. `PasswordInputTest` pins it.

## Composite editors go two-column from xl
The benchmark case form (`Admin/Benchmarks/Cases/Form`) and the chat template editor (`AI/Templates/Edit`) are `max-w-[900px]` single columns below `xl` and lift the cap and become a CSS grid from `xl` (1280 px) up. Every block is placed with `xl:col-start-*` and `xl:[grid-row:...]` utilities on the same elements, so the DOM order, and with it the tab order below `xl`, never changes and no block is duplicated. Rows that depend on optional blocks (the case form's draft warning, the template editor's variable ledger) use a CSS variable set from a computed `:style` instead of fixed row numbers, and a `minmax(0,1fr)` spacer row absorbs the height difference between columns (the fixtures take `xl:-mt-6` to cancel the extra row gap). The template editor puts the live Preview in the right column, `sticky` below the header (`xl:top-17`) with its own `max-height` and scroll, so a tall editor never pushes it out of view. `SideBySideEditorsTest` pins both pages at 1440 px and the single column at 1279 px.
