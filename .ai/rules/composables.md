# Composables

## Composables
Name the file and its named export `useX`; export a `function`, never a default or arrow const. Declare and export an explicit `UseXReturn` type for the returned object. Composables owning an Echo/Reverb channel expose `subscribe`/`unsubscribe` and self-release from `onUnmounted`, and join a channel only when `useCan()` grants the ability `routes/channels.php` checks (`useNotifications` and `useNavCounts` join `members.actions` under `manage-library`): a refused join logs a console error on every page. `ViewerAccessTest` pins it.

## Live rows carry per-reader fields through map
`useRealtimeList({ channel, event, keyField, map })` takes one channel or a list (every channel feeds one list, deduplicated by `keyField`) and an optional `map(payload) => row`. A broadcast goes to every reader, so it can never carry a per-reader field the page's resource computes per request (`can_toggle_played`): broadcast the fact the rule needs (`EmbyPlaybackUpdated.user_id`, the Emby link's owner) and derive the field in `map` with the same rule as the model (`EmbyActivity::playedStateEditableBy()`), leaving the server to re-check on submit. Without `map`, a pushed row that replaces a server row silently drops the field. A list whose rows carry an order passes `replaces(current, incoming)` too: an event for a row already listed replaces it only when the rule allows (default: always), so a broadcast delivered late cannot roll a newer row back; a row not yet listed is always added. The Action Queue passes `pushedRowIsCurrent()` (`ActionQueueLiveListTest`).

## Sidebar badge counts are absolute and survive a prefetch
`useNavCounts` takes the pending-actions badge from `pending_count` on `ActionRequestCreated` / `ActionRequestStatusChanged` (every pending request when the queued broadcast ran), never from per-id deltas, which could not lower it for a request pending before the tab opened. The pending count is also versioned: `pending_version` on the broadcasts and `pendingActionsVersion` in `nav` (both from `PendingActionCount::snapshot()`) are the newest `status_version` behind the count. `useNavCounts` keeps the version the badge shows and when it arrived, and ignores a count with an older version (parallel queue workers publish out of order). A `nav` snapshot overwrites the pending counter when its version is at least the badge's, or — for the response to a request that brings `nav` (a full visit, or a reload that names it), re-applied on `success` — when that request started after the badge's version arrived: it read the database later than the broadcast did, so a lower version there means the versions went backwards (a restored database, a bogus payload) and the server must win, or the badge would stay wrong until a hard reload. A visit that started before a newer broadcast yields to it, and so does every snapshot that sends no request of its own (a prefetch a click reuses, a history back/forward restore). A count or snapshot without a version (an older worker, a history entry from before versions) makes the version unknown and falls back to the client-clock rule below. `NavBadgeOrderTest` pins it. A `nav` snapshot overwrites a counter only if no live event moved that counter after the snapshot was produced: a response to a request just sent counts as "now", a click that reuses a hover prefetch counts as the prefetch's `fetchedAt` (`router.on('prefetched')`). Never forget that date when a real request for the URL starts: Inertia flushes a URL's cached prefetch only when a non-prefetch response for that URL completes (`Response.process()` → `router.flush()`), so a request still in flight when the user navigates away — the page's own deferred-prop reload, which the navigation cancels — leaves the prefetch reusable for the rest of its `cacheFor` window. A test of that case holds the reload in flight (`PrefetchTest`); one that lets it land sees the next click send a fresh visit. Do drop it once that window has passed (`PREFETCH_CACHE_MS`, matching `app.ts`'s `cacheFor`): no click can reuse the prefetch after it, and the map would otherwise grow all session. Instead, every request that brings `nav` (a full visit, or a reload whose `only` names it) re-applies it as "now" on `success` (for the pending counter, under the version rule above). A page that changes counts through a JSON request, not a visit (the Action Queue's bulk run), reloads `nav` with its own props. A component that lives on every page (the chat panel's inline Approve/Reject) does not: a reload there re-runs whatever page is open, and the queued `ActionRequestStatusChanged` broadcast moves the badge instead. `PrefetchTest` and `ActionQueueBulkTest` pin both.

## A dialog's fetch aborts on close and on reopen
A composable that fetches into a dialog (`useInvocationDetail`) holds one `AbortController`: opening again aborts the request in flight, closing aborts it and clears the loading flag, a result or error from an aborted request is dropped, and `onUnmounted` aborts. A dialog that stays open while loading otherwise cannot be closed, and a late answer reopens it or overwrites a newer one. `AiUsageDetailAbortTest` pins it with a fetch held back in the page.
